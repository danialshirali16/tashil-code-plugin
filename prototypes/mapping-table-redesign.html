Implementation mapping — redesign options

Three directions for the mapping table, using your real Button data. Same information in all three; they differ in how much is shown at once and where editing happens.

What's wrong with the current table
  • The suggestion note is orphaned. "Suggested: Figma property size matches size" sits below the value rows and directly above color — it looks like it belongs to the wrong prop.
  • "Not mapped" shouts. It's the default state repeated seven times at full contrast, so the eye can't find what's actually done or what needs work.
  • Everything is expanded forever. Value pairs stay open once a property is chosen, so eight props scroll far beyond one screen.
  • Weak hierarchy. Value pairs look almost like sibling rows rather than children of their prop.
  • The ← reads backwards and the decorative › adds noise.
  • Type names cost a whole line under every prop name.
  • No sense of progress — nothing tells you how close to done you are.
Option A

Compact table, inline pairs

Closest to today, tightened. Type becomes an inline badge, unmapped rows are dimmed instead of loud, the suggestion attaches directly under the row it belongs to, and value pairs are visually nested. Least disruptive; still long for big components.

Option B — recommended

One line per prop, expand to edit

Every prop collapses to a single line showing what it resolves to right now. Click to expand and edit; only what you're working on is open. A status dot makes done / to-do / needs-attention scannable. Eight props fit on one screen, and it scales to InfoModal's 27.

Option C

List left, editor right

The prop list stays scannable on the left; all editing happens in a fixed pane on the right. Best for long components — the list never grows as you edit. Costs horizontal space, which is tight in a Figma plugin panel.

My recommendation: Option B. It fixes every problem listed above without needing horizontal space the plugin panel doesn't have, and it's the only one that stays usable at InfoModal's 27 props. Option A is the safest if you want a smaller change; Option C is strongest for very long lists but cramped at typical plugin widths.

All three keep the rules already built: code props stay the primary column, one control per target, per-value pairs, suggestions requiring review, and constrained static values.
