Mapping — structural rethink

You were right: the last three were one model (a list of code props, each with a dropdown) in three arrangements. These three change the model itself. Same Button data throughout.

What the old model gets wrong, structurally. It shows one side only. The Figma component — the thing you are connecting to — never appears; it is hidden inside dropdown options. So you cannot see what Figma offers, what you have already used, or what you are ignoring. And the result you are building is a preview at the bottom rather than the thing you work on.
Direction 1

Connect board — both sides visible

The Figma component and the code API sit side by side as two real inventories. Every item shows whether it is connected, so you can see at a glance what Figma offers that you have not used (State, hasIcon) and what code still needs. Selecting a connection opens its value pairs underneath. This is the only direction where "connect" is literal.

Direction 2

Code canvas — edit the result directly

The generated TSX is the editor. Each prop value is a token you click to bind; unmapped props wait in a tray below instead of padding the list. You are always looking at exactly what a developer will copy, so there is no gap between "the table" and "the output". Shortest possible surface — only what you have decided takes space.

Direction 3

Focused queue — one decision at a time

Instead of a table you triage yourself, the plugin asks about one prop at a time, in priority order, phrased as a question with real options rather than an empty dropdown. Everything already decided collapses out of the way. Best for a first connection; weakest for going back and adjusting one thing later.

My pick: Direction 1. You said Option C's two-pane split felt right — this keeps that shape but makes the left pane the Figma component itself rather than another list of code props. That is the actual structural change: both sides of the connection become visible, unused Figma properties stop being invisible, and value pairs get a proper home instead of being nested inside a row.

Direction 2 is the boldest and the best answer to "the output is what matters", and would pair well with 1 as the preview. Direction 3 is worth stealing one idea from regardless: phrasing the choice as a question with named options beats an unlabelled dropdown.
